## A-6 in detail

1. `claude plugin marketplace add ~/cdp6-probe-kit` reports "declared in user settings", which reads as an entry in `~/.claude/settings.json`; the file was not inspected while the marketplace was added.
2. `claude plugin install cdp6-core@cdp6-probe --scope project` in scratch project A resolves the relative source `./cdp6-core` and writes `{"enabledPlugins": {"cdp6-core@cdp6-probe": true}}` to `A/.claude/settings.json`.
3. The first session in A, the one that showed the workspace trust dialog, did not load the plugin (not listed in `/plugin`, no log line). The next sessions in A loaded it (SessionStart with cwd A), with and without a local file that sets its own `enabledPlugins` object: the project and local `enabledPlugins` objects merge per key.
4. Scratch project B, in its second session after trust: no `cdp6-core` in `/plugin`, `/hooks` "33 events · 0 with hooks", no log line. Project scope does not reach B: green.
5. Stage-1 variant: `claude plugin install cdp6-core@cdp6-probe --scope local` run inside the probe worktree created `main/.claude/settings.local.json` at the main checkout's root with `{"enabledPlugins": {"cdp6-core@cdp6-probe": true}}`; the worktree's own local file stayed unchanged; `installed_plugins.json` names the worktree as `projectPath`. A session in the main checkout then loaded the plugin ("Local" in `/plugin`, SessionStart and PreToolUse lines with cwd main). B stayed clean. Red (owner to confirm the classification): the concept row's expected record (plugin inactive in B) was met, but the local-scope install from the worktree could not place `enabledPlugins` in the probe worktree's local file and enabled the plugin in the main checkout; by the docs ("In a worktree, it uses the file at the main checkout's root", settings.md, not measured) it reaches every worktree.
6. Cleanup: both installs and the marketplace removed (`marketplace remove` also reported "Also uninstalled 1 plugin" although both installs were already removed); the created main-root file, scratch projects and orphaned cache deleted.

- Sandboxed commands run without a permission prompt; that an excluded command goes through the permission flow is the docs statement (sandboxing.md:176), not separately measured (every A-5 prompt came with the guard's `ask`).
- A `cd` in a Bash call carries the working directory into the next call; briefs and scripts must use absolute paths or `git -C`.
- The sandbox proxy requires the credentials of the `HTTPS_PROXY` URL userinfo (`407` without them).
- `node` built-in `fetch` ignores `HTTPS_PROXY`; inside the sandbox it fails name resolution (`EAI_AGAIN`).
- In 2.1.314 the CLI calls the default mode "manual"; hook inputs report `permission_mode` `default`.
- Hooks run through `/bin/sh` with the `PATH` of the `claude` process.
